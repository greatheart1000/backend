```
## 模块详细说明

### 0. 文档处理模块 (DocumentProcessor)
- **功能**: 文档切分、分层处理和向量化
- **输入**: 原始文档内容
- **输出**: 结构化文档块（大块和小块）
- **存储**: Elasticsearch索引
- **依赖**: SentenceTransformer嵌入模型

### 1. 意图识别模块 (IntentClassifier)
- **功能**: 分析用户查询的意图类型并确定检索权重
- **输入**: 用户查询文本
- **输出**: 意图类别(A/B/C/D)和BM25/Vector权重
- **缓存**: 缓存A存储意图识别结果
- **依赖**: Transformers库，零样本分类模型

### 2. 上下文管理模块 (ContextManager)
- **功能**: 管理查询向量化和会话历史
- **输入**: 查询文本，会话ID
- **输出**: 查询向量，会话历史
- **缓存**: 缓存D存储查询向量，缓存E存储会话历史
- **依赖**: SentenceTransformers库

### 3. 动态检索模块 (DynamicRetriever)
- **功能**: 执行混合检索(BM25+向量检索)
- **输入**: 查询文本，查询向量，检索权重
- **输出**: 候选文档列表
- **缓存**: 缓存B存储候选ID列表
- **依赖**: Elasticsearch

### 4. 精排与融合模块 (Reranker)
- **功能**: RRF融合和交叉编码器精排
- **输入**: 查询文本，候选文档
- **输出**: 精排后的Top K文档
- **缓存**: 缓存C检查是否有最终答案
- **依赖**: SentenceTransformers库(BGE Reranker)

### 5. 答案生成模块 (AnswerGenerator)
- **功能**: 基于文档生成自然语言答案
- **输入**: 查询文本，精排文档，上下文信息
- **输出**: 自然语言答案
- **缓存**: 缓存C存储最终答案
- **依赖**: Qwen API

### 6. 缓存管理模块 (CacheManager)
- **功能**: 统一缓存管理接口
- **输入**: 缓存键值对
- **输出**: 缓存数据
- **依赖**: Redis

## 文档处理流程

### 分层切块策略

系统采用分层文档切块策略，生成不同粒度的文档块：

#### 大块（Large Chunks）
- **大小**：1000字符
- **重叠**：100字符
- **用途**：保持段落完整性，适合长文本理解

#### 小块（Small Chunks）
- **大小**：300字符
- **重叠**：30字符
- **用途**：提高检索精度，适合精确匹配

### 向量化处理

所有文档块都会进行向量化处理：
- **模型**：SentenceTransformer (all-MiniLM-L6-v2)
- **维度**：384维向量
- **存储**：与文档块一起存储在Elasticsearch中
- **用途**：支持语义相似度检索

## 五级缓存设计详解

### 缓存层次结构的意义

RAG系统采用五级缓存设计，每一级都有其特定的优化目标和价值：

#### 第一级缓存A（意图/权重）
- **优化目标**: 减少意图分类计算开销
- **适用场景**: 对于重复或相似的查询，避免重复调用意图分类模型
- **性能提升**: 节省LLM或分类模型的推理时间（通常数百毫秒到数秒）
- **技术实现**: 缓存查询哈希值对应的意图分类结果和BM25/向量检索权重

#### 第二级缓存B（候选ID列表）
- **优化目标**: 减少检索阶段的数据库查询开销
- **适用场景**: 相同查询的混合检索结果可直接复用
- **性能提升**: 节省Elasticsearch的BM25和向量检索时间（通常数百毫秒）
- **技术实现**: 缓存混合检索返回的文档ID列表及其相关性得分

#### 第三级缓存C（最终答案）
- **优化目标**: 最大化热点查询的响应速度
- **适用场景**: 完全相同的查询可直接返回缓存结果
- **性能提升**: 从秒级响应优化到毫秒级响应
- **技术实现**: 缓存完整答案文本，直接返回给用户

#### 第四级缓存D（查询向量）
- **优化目标**: 减少文本向量化计算开销
- **适用场景**: 相同查询的向量表示可直接复用
- **性能提升**: 节省SentenceTransformer的推理时间（通常几十到几百毫秒）
- **技术实现**: 缓存文本到向量的映射结果，避免重复计算

#### 第五级缓存E（会话历史）
- **优化目标**: 维护对话上下文连贯性
- **适用场景**: 多轮对话中的上下文理解
- **性能提升**: 避免重复的会话状态管理开销
- **技术实现**: 缓存用户会话历史记录，支持上下文增强查询

### 每级缓存的具体作用

1. **缓存A（意图/权重）**:
   - 作用：避免重复意图识别计算
   - 场景：相同或相似查询的意图分类
   - 价值：节省模型推理资源，提升分类效率

2. **缓存B（候选ID列表）**:
   - 作用：避免重复检索操作
   - 场景：相同查询的文档检索
   - 价值：减少数据库负载，提升检索效率

3. **缓存C（最终答案）**:
   - 作用：直接返回热点答案
   - 场景：高频重复查询
   - 价值：极致响应速度，优化用户体验

4. **缓存D（查询向量）**:
   - 作用：避免文本向量化重复计算
   - 场景：相同查询的向量表示
   - 价值：节省嵌入模型计算资源

5. **缓存E（会话历史）**:
   - 作用：维护对话上下文
   - 场景：多轮对话交互
   - 价值：提供连贯的对话体验

### 语义相似度缓存扩展

系统支持基于语义相似度的智能缓存匹配：

1. **精确匹配**：完全相同的查询直接返回缓存结果
2. **语义匹配**：语义相似但表达不同的查询可复用相关缓存
3. **阈值控制**：通过配置相似度阈值平衡准确性和命中率

### Redis Cluster支持

系统支持Redis Cluster部署以处理大规模并发场景：

``mermaid
graph LR
    A[应用服务器] --> B[Redis Cluster]
    B --> C[节点1]
    B --> D[节点2]
    B --> E[节点3]
    
    subgraph Redis Cluster
        C
        D
        E
    end
```

优势：
- **水平扩展**：支持动态增减节点
- **高可用性**：自动故障转移
- **性能优化**：分布式存储和计算

### 缓存策略优势

1. **分层优化**: 不同缓存层级针对不同计算瓶颈进行优化
2. **粒度控制**: 精细化的缓存粒度允许更精准的缓存命中
3. **成本效益**: 根据计算成本和复用频率合理分配缓存资源
4. **用户体验**: 多层次缓存显著提升系统响应速度和用户体验

## 数据流向

```
sequenceDiagram
    participant U as 用户
    participant P as Pipeline
    participant C as 缓存层
    participant S as 存储层
    participant M as 模型层
    
    U->>P: 提交查询
    P->>C: 检查意图缓存
    alt 缓存未命中
        P->>M: 意图分类
        M-->>P: 返回意图和权重
        P->>C: 缓存意图结果
    end
    
    P->>C: 获取查询向量和会话历史
    alt 向量未缓存
        P->>M: 文本向量化
        M-->>P: 返回向量
        P->>C: 缓存向量
    end
    
    P->>S: 混合检索
    S-->>P: 返回候选文档
    P->>C: 缓存候选列表
    
    P->>C: 检查最终答案缓存
    alt 答案未缓存
        P->>M: 精排和融合
        M-->>P: 返回精排结果
        P->>M: 调用大模型生成答案
        M-->>P: 返回答案
        P->>C: 缓存最终答案
    end
    
    P->>C: 更新会话历史
    P->>U: 返回答案
```

## 相似查询处理机制

### 缓存命中策略

系统采用多层次的缓存命中策略来处理相似查询：

1. **精确匹配**：使用查询内容的哈希值作为缓存键，确保完全相同的查询能够直接命中缓存
2. **部分复用**：对于相似但不完全相同的查询，复用部分中间结果（如意图识别、向量表示等）
3. **完整处理**：对于全新的查询，执行完整的RAG流程并缓存结果

### 高级语义相似度匹配

系统通过以下方式实现语义相似度匹配：

1. **向量计算**：将查询转换为向量表示
2. **相似度计算**：计算余弦相似度
3. **阈值匹配**：超过阈值则复用缓存
4. **快速返回**：直接返回相似查询的答案

```
# 伪代码示例
def semantic_similarity_cache(query_vector):
    # 获取所有缓存的查询向量
    cached_vectors = redis.get_keys_by_pattern("query_vector:*")
    
    for cached_key in cached_vectors:
        cached_vector = redis.get(cached_key)
        similarity = cosine_similarity(query_vector, cached_vector)
        
        # 如果相似度超过阈值(如0.95)
        if similarity > 0.95:
            # 获取对应的答案缓存键
            answer_key = cached_key.replace("query_vector:", "final_answer:")
            return redis.get(answer_key)
    
    return None
```

### 处理流程示例

#### 场景1：完全相同查询
```
用户: "什么是人工智能？"
系统: 检查所有缓存层 → 缓存C命中 → 直接返回答案（毫秒级响应）
```

#### 场景2：语义相似查询
```
用户: "人工智能是什么？"（首次）
系统: 
  1. 精确缓存未命中
  2. 执行语义相似度搜索
  3. 发现与"什么是人工智能？"相似度0.96
  4. 直接返回缓存答案
  5. 响应时间：100-300毫秒
```

#### 场景3：相关查询（上下文）
```
用户: "什么是机器学习？"
系统: "机器学习是人工智能的一个分支..."
用户: "它有哪些应用？"（基于上下文）
系统: 
  1. 从会话历史缓存E获取上下文
  2. 理解"它"指代"机器学习"
  3. 执行针对"机器学习应用"的检索
  4. 生成相关答案
```

这种设计确保了系统既能快速响应重复查询，又能通过语义相似度匹配处理表达不同但含义相同的查询，提供优质的用户体验。

## 性能优化策略

1. **多级缓存**: 减少重复计算，提高响应速度
2. **向量缓存**: 避免重复的文本向量化操作
3. **结果缓存**: 对相同查询直接返回缓存结果
4. **会话管理**: 利用上下文提升对话质量
5. **混合检索**: 结合BM25和向量检索的优势
6. **精排优化**: 使用RRF融合和交叉编码器提升精度
7. **文档分层**: 大块保持上下文，小块提高精度
